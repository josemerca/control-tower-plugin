# F25 — `/ct-status`: plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** un comando que responde de una sola llamada «qué está en vuelo, qué ha entregado, qué es residuo», incluyendo si un slice en vuelo tiene de verdad un proceso trabajando — hoy el coordinador lo compone a mano cada vez, y ya costó reportar 6 casos cuando eran 10.

**Architecture:** I/O en el borde, decisiones puras. `scripts/liveness.js` reúne las señales locales (worktree, rama, cmux, **proceso**); `scripts/loop-estado.js` es una función **sin I/O** que recibe señales y devuelve los tres cubos; `scripts/ct-status.mjs` es el CLI delgado que hace las llamadas, invoca al compositor, renderiza y elige el código de salida.

**Tech Stack:** Node ESM, vitest, `gh` (REST + timeline), `pgrep`/`lsof`, git.

**Spec:** `docs/superpowers/specs/2026-08-04-ct-status-design.md`

## Hechos verificados empíricamente antes de escribir este plan

No los re-deduzcas; puedes re-comprobarlos. Cuatro de ellos habrían sido bugs:

1. **`pgrep -x claude` sale con `rc=1` cuando no hay ninguno**, y `execFileSync` lanza ante un exit no-cero. Hay que distinguir `e.status === 1` («ninguno», respuesta normal y válida) de un fallo real. Sin eso, **un loop en reposo daría falsa alarma de exit 1 en cada corrida**.
2. **`lsof -a -p "" -d cwd -Fpn` devuelve basura**: con la lista vacía listó un proceso ajeno (`p414` / `n/`). La lista vacía se corta ANTES de llamar.
3. **Una sola llamada agrupada de `lsof` cuesta 52 ms** y devuelve tripletes `p<pid>` / `fcwd` / `n<ruta>`. Un PID que muere entre el `pgrep` y el `lsof` no la rompe: sale con 0 y lo omite.
4. **`pgrep -x`, nunca `-f`:** `-f` casa cualquier línea de comando que contenga «claude», incluida la del propio comando que comprueba.
5. **El timeline da la edad exacta del claim.** `gh api repos/<o>/<r>/issues/<n>/timeline --paginate`, filtrando `event == "labeled" && label.name == "status:in-progress"`, y quedándose con el ÚLTIMO. Verificado contra un issue real: `2026-08-01T11:38:19Z`. Las labels **no** llevan fecha en el payload REST del issue; comprobado.
6. **Dos de las cuatro piezas que el spec creía extraíbles ya son puras:** `collectFinishedResidue` (`scripts/dispatch.js`) y `closedWithLiveStatus` (`scripts/gh-issue-map.js`). Se importan y ya está.
7. **El `cwd` de un agente puede ser más profundo que la raíz del worktree** (`.worktrees/9/apps/backend`). El mapeo toma el segmento que sigue a `.worktrees/`, no la ruta completa.

**Presupuesto de la ventana de arranque:** `DEFAULT_LAUNCH_SENTINEL_TIMEOUT_MS` en `scripts/ct-next.mjs` vale hoy **15000**.

```js
import { execFileSync } from 'node:child_process'

const ejecutar = (cmd, args) => execFileSync(cmd, args, { encoding: 'utf8', stdio: ['ignore', 'pipe', 'pipe'] })

// liveSliceProcesses: ¿qué slices tienen AHORA MISMO un proceso `claude`
// trabajando dentro de su worktree? Es la pregunta que ninguna otra señal del
// loop responde: al morir, un agente deja worktree, rama y ventana de cmux en
// su sitio, así que todo lo demás sigue diciendo "vivo".
//
// `pgrep -x`, nunca `-f`: `-x` casa el nombre exacto del proceso, mientras que
// `-f` casa cualquier línea de comando que contenga "claude" — incluida la del
// propio comando que hace esta comprobación.
//
// Una sola llamada a `lsof` para todos los PID (medido: 52 ms). Un PID que
// muera entre el `pgrep` y el `lsof` no rompe nada: lsof sale con 0 y
// simplemente lo omite.
export function liveSliceProcesses(repoRoot, { run = ejecutar } = {}) {
  let pids
  try {
    pids = run('pgrep', ['-x', 'claude']).split('\n').map((s) => s.trim()).filter(Boolean)
  } catch (e) {
    // rc=1 en pgrep significa "ninguna coincidencia", que es una respuesta
    // NORMAL y válida: el loop en reposo no tiene agentes. Tratarla como
    // fallo daría falsa alarma en cada corrida tranquila.
    if (e && e.status === 1) return { porSlice: new Map(), comprobado: true, motivo: null }
    return { porSlice: new Map(), comprobado: false, motivo: `no se pudo listar procesos con pgrep: ${e && e.message}` }
  }
  // Sin PID no se llama a lsof, y no es una optimización: medido, `lsof -a -p ""`
  // devuelve un proceso AJENO en vez de nada, así que la lista vacía produciría
  // un falso positivo.
  if (!pids.length) return { porSlice: new Map(), comprobado: true, motivo: null }

  let salida
  try {
    salida = run('lsof', ['-a', '-p', pids.join(','), '-d', 'cwd', '-Fpn'])
  } catch (e) {
    return { porSlice: new Map(), comprobado: false, motivo: `no se pudo leer el directorio de trabajo de los procesos con lsof: ${e && e.message}` }
  }

  // `-Fpn` emite tripletes: p<pid> / fcwd / n<ruta>.
  const porSlice = new Map()
  const prefijo = `${repoRoot}/.worktrees/`
  let pidActual = null
  for (const linea of salida.split('\n')) {
    if (linea.startsWith('p')) { pidActual = linea.slice(1); continue }
    if (!linea.startsWith('n') || pidActual === null) continue
    const cwd = linea.slice(1)
    const pid = pidActual
    pidActual = null
    if (!cwd.startsWith(prefijo)) continue
    // El agente puede haberse metido MÁS ADENTRO del worktree, así que se toma
    // el primer segmento tras `.worktrees/`, no la ruta entera.
    const slice = cwd.slice(prefijo.length).split('/')[0]
    if (slice && !porSlice.has(slice)) porSlice.set(slice, pid)
  }
  return { porSlice, comprobado: true, motivo: null }
}
```

Crear `scripts/loop-estado.js`. La cabecera explica por qué es puro:

```js
// Composición del estado del loop: recibe señales ya recogidas y devuelve los
// tres cubos del informe. NO hace I/O — ni red, ni procesos, ni disco.
//
// Está separado del comando a propósito: todas las decisiones que importan
// —quién está vivo, quién sólo está arrancando, qué worktree no reclama nadie,
// y si hay algo que revisar— se toman aquí, y por tanto se pueden probar sin
// montar un repo, sin lanzar procesos y sin red.
//
// Tres estados para "¿está vivo?", no dos: `true`, `false`, y `null` cuando no
// se pudo comprobar. Colapsar el tercero en `false` convertiría una herramienta
// que falta en una acusación de abandono.
```

Reglas a implementar, todas cubiertas por los tests de arriba:
- `vivo`: `null` si `!procesos.comprobado`; si no, `porSlice.has(String(n))`.
- `arrancando`: sólo si `vivo === false`, la edad se conoce, y `edad < ventanaArranqueMs`.
- Un `enVuelo` cuenta como hallazgo si `vivo === false && !arrancando`.
- Edad desconocida (`null`) con `vivo === false` → no se acusa; entra en `sinComprobar` nombrando el issue.
- `procesos.comprobado === false` → su `motivo` entra en `sinComprobar`.
- `cosecha`: los `mergeados` que tienen worktree o rama.
- `worktreesHuerfanos`: los de disco que no explica ni un `enProgreso` ni un `mergeado`.
- `hayHallazgos`: cosecha, residuo (labels o huérfanos), o algún `enVuelo` sin vida y sin arrancar.
